## §21 미확정 항목에 대한 판단 재료

**1단계(분석·설계) 자동 생략 기준.** #1은 "한 문장으로 설명되는 변경"이고, 에이전트가
읽기 → 수정 → 테스트 → 커밋을 56초에 끝냈다. 여기에 분석 Run을 먼저 두면 실행보다
분석이 더 길어진다. #2는 분석이 있었다면 모순을 실행 전에 잡았을 것이다 — 하지만 실행
단계가 스스로 잡아서 멈췄고, 그 보고서의 질이 분석 보고서와 다르지 않았다.
→ **기본은 켬이되 "본문이 짧고 완료조건이 한 줄" 이면 생략** 이 맞아 보인다. 판정은 라벨보다
본문 길이가 실제에 가깝다(#1 본문 1문장, #2 본문 2문장 — 둘 다 생략 대상이었고 둘 다
문제없이 끝났다). 임계값은 더 큰 이슈를 돌려 봐야 정할 수 있다.

**3단계(회고) 별도 Run 기준.** 세 번 모두 에이전트의 마지막 메시지가 "무엇을 바꿨고 왜,
판단이 들어간 부분" 을 이미 요약했다(#2′의 "빈 패키지 선언 유지" 판단까지). 작은 변경에서
별도 회고 Run은 같은 내용을 두 번 쓰는 것이다.
→ **기본은 2단계의 꼬리** 로 충분하다는 관측. 별도 Run은 diff가 크거나 여러 파일에 걸칠
때만 — 기준은 역시 더 큰 이슈에서.

## 발견한 것

1. **attention 파일 프로토콜이 프롬프트 지시만으로 작동한다.** 에이전트가 파일을 쓰고
   정상 종료했고, 보고서는 사람이 결정할 수 있는 형태였다. 파일 기반 신호를 계속 쓴다.
2. **`--resume`이 맥락을 실제로 잇는다.** 2′는 이전 세션의 분석을 다시 하지 않고 "(a)에
   따라" 로 바로 시작했다. 이어서 재시도의 가치가 확인됐다.
3. **승인 피로.** 3줄짜리 변경에 승인 5회(Edit 2, Bash 3). 첫 `Bash`(읽기)는 승인 없이
   지나갔는데, 이는 사용자의 전역 permission 규칙이 허용한 것이다. 프로젝트별 사전 허용
   도구(PRD §11.6.3, `--allowedTools`)가 Phase 1의 실사용 조건이다 — 지금은 스크립트로
   전부 허용했지만 사람이 손으로 5번 누르는 건 첫날부터 짜증이 난다.
4. **웹 UI의 승인 화면은 SSE 아일랜드에만 `request_id`가 있다.** 서버 렌더링 HTML에는
   없어 스크립트가 SSE를 구독해야 했다. 사람이 브라우저로 쓰는 데는 문제없지만, API로
   승인하려면 `GET /runs/{id}/approvals` 같은 조회가 필요하다.
5. **`default.profraw`가 worktree마다 생긴다.** 에이전트가 `go test`를 돌릴 때 이 머신의
   Go 환경이 만든 것으로 보인다(이 저장소 `.gitignore`에 `*.profraw`가 있는 이유와 같다).
   에이전트는 "작업 전부터 있던 파일" 로 인식하고 손대지 않았다. Taskyard 문제는 아니다.
6. **기본 템플릿의 PR 단계는 원격이 없는 저장소에서 막힌다.** 이번엔 템플릿에서 뺐다.
   프로젝트 설정에 "PR 생성 여부" 를 두거나, 러너가 원격 유무를 알려 템플릿이 분기하게 하는
   것이 merge 정책 PR의 일부가 되어야 한다.
7. **이슈 상태 전이가 관측대로 움직였다.** #1 succeeded → review, #2 needs_attention →
   in_progress 유지, #2′ succeeded → review. 재시도 Run의 `previous_run_id`·`feedback`·
   `workspace_run_id`가 원장에 남았다.
